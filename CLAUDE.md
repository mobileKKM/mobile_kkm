# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository.

## What this is

mobileKKM: an unofficial GPL-3.0 Flutter client (Android + iOS) for the mKKM / EKP ticketing backend of ZTP / MPK Kraków, reverse-engineered from the official Android app. A [pub workspace](https://dart.dev/tools/pub/workspaces) of three members, dependency direction app → `ekp_api` → `ekp_crypto`:

- `.` (`mobile_kkm`) — the app. Built: theme, splash, signed-out flows (login, registration, password reset, e-mail links), the mKKM card set-up, and the signed-in shell (Home, Tickets, Map, Account) with a hidden debug menu. Tickets: details, return, line change, ticket control (AZTEC), the purchase (choose, check and pay, tPay in a Custom Tab / Safari view, awaiting payment). Karta Krakowska: status and status code. Account: edit, change password, delete. Map: MapLibre map of Kraków, search placeholder, position button.
  Not built: vehicles, stops with departures, stop search; noticing the connection is back (only start-up and pull-to-refresh ask again; planned: a `connectivity_plus` listener calling `AppStatusController.check()`); 5+1 (`/subscription`, `ComingSoonScreen`); the design's first-start notice (11h).
- `packages/ekp_api` — pure-Dart `dio` client, no Flutter.
- `packages/ekp_crypto` — pure-Dart crypto for `assign-e` / `contract-e` (RSA-wrapped requests, AES-128-CBC contract → AZTEC token).

`docs/official-app/` reconstructs the official client's screens, button rules and requests from its decompiled bundle (`.dumps/react/`). Read the relevant document before building a feature the official app has; its README maps modules to the original code.

## Release

Application ID `de.codebucket.mkkm`.

```bash
flutter build apk --release --target-platform android-arm,android-arm64 --split-debug-info=build/symbols
    # direct download / F-Droid; not --split-per-abi, which adds 1000 × ABI to the version code (above Play's)
flutter build appbundle --release   # Google Play, all three ABIs
```

- The APK (~31 MB) leaves out x86_64 and compresses native libraries (`useLegacyPackaging`). `--target-platform` alone doesn't limit MapLibre's prebuilt libraries, so `build.gradle.kts` sets `abiFilters` from Flutter's `target-platform` Gradle property. `build/symbols` + `flutter symbolize` decodes stack traces.
- `--dart-define=AZTEC_KEY_RELAY_URL=https://…` (no path; `flutter run` too) uses another relay than `relay.mobilekkm.app`; `AZTEC_KEY_RELAY_TOKEN` when it has `RELAY_API_TOKEN` set (the token is readable from the built app).
- Signing: `android/key.properties` (gitignored: `storeFile`, `storePassword`, `keyAlias`, `keyPassword`). Without it the release build uses the debug key — never publish that. Raise the `+N` in `pubspec.yaml` for every upload (the old WebView app under this ID reached 23). The APK omits AGP's `dependenciesInfo` (F-Droid rejects it); the bundle keeps it.
- `ci.yml` (pushes to `main`, PRs): format, `dart analyze --fatal-infos`, generated code vs the commit, the three suites, a release APK with and without GMS (`strip_gms.sh` in its own pub cache, then `tool/ci/check_no_gms.sh` on Gradle's dependency graph, since R8 hides GMS classes). Flutter is pinned in `.github/actions/setup-flutter/action.yml`; keep it equal to the F-Droid recipe's `srclibs`. Java 21 (maplibre_gl compiles for it; the app targets 17).
- `release.yml` (tag `v<version name>`): the checks, tag vs `pubspec.yaml`, `mobileKKM-<name>-gms.apk` and `-foss.apk` (same ID, code and key, so either updates the other), `tool/ci/check_signer.sh` against `RELEASE_CERT_SHA256`, symbols artifacts, and a **draft** release with `SHA256SUMS`, notes from `fastlane/metadata/android/en-US/changelogs/<versionCode>.txt` (else GitHub's), pre-release when the name has a `-`. The `.aab` is only an artifact, uploaded to Play by hand. `workflow_dispatch` builds and signs without releasing. Environment `release` (tags `v*`, `main`): secrets `ANDROID_KEYSTORE_BASE64` (`base64 -i <keystore>`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, optional `AZTEC_KEY_RELAY_TOKEN`; variables `RELEASE_CERT_SHA256` (`keytool -list -v`, colons optional), optional `AZTEC_KEY_RELAY_URL`. Relay settings reach the build via `--dart-define-from-file`, only those set (an empty address would replace the default). A missing secret stops the build rather than signing with the debug key.
- Store listing: `fastlane/metadata/android/{en-US,pl-PL}/` (no fastlane tool; F-Droid reads it, the Play Console is filled from it by hand). Each release adds `changelogs/<versionCode>.txt` to both (≤ 500 chars); short description ≤ 80; title ≤ 30, "<app name>: <what it does>". The full description sticks to the core features (eKP account, mKKM card, offline tickets, live map, free software); the first release waits for the map and the purchase. Karta Krakowska is only a note; 5+1 stays out until built. `icon.png` / `featureGraphic.png` are the old app's; screenshots wait for a demo mode.
- F-Droid: `tool/fdroid/de.codebucket.mkkm.yml` drafts the recipe; its `prebuild` runs `tool/fdroid/strip_gms.sh` on `geolocator_android` and `maplibre_gl` (pinned by `pubspec.lock`; it breaks when a plugin update moves the patched code, which CI's no-GMS build catches).

## Privacy constraints

- `.dumps/` holds raw captures with real credentials and personal data: gitignored, never commit it, never copy values from it into fixtures, tests, docs or commit messages.
- `packages/ekp_api/test/fixtures/` is sanitized; keep new fixtures synthetic. `packages/ekp_api/tool/` (fixture extraction) is deliberately gitignored.
- `ekp_crypto` tests use synthetic vectors; `packages/ekp_crypto/tool/make_synthetic_contract.dart` regenerates the contract fixture `ekp_api` uses.

## Architecture

### `ekp_api`

- `EkpClient` (`lib/src/ekp_client.dart`): one `Dio` pipeline (cookie jar → `DeviceHeadersInterceptor` → `AuthInterceptor`) and one API object per domain (`auth`, `account`, `tickets`, `payments`, `subscriptions`, `dictionaries`, `storageMediums`, `invoices`, `misc`), each in `lib/src/<domain>/` as `<domain>_api.dart` + `<domain>_models.dart`.
- Services extend `EkpApiService` and wrap calls in `guard()`, which maps `DioException` to the sealed `EkpApiException` (`EkpNetworkException`, `EkpUnauthorizedException`, `EkpHttpException`, `EkpSessionExpiredException`). Callers never see `DioException`.
- Request bodies are explicit maps; response models (`freezed` + `json_serializable`) mirror the wire format exactly, inconsistencies included (`code` is `Object?`). Don't tidy them.
- `EkpSessionManager`: persists through the host's `TokenStore`, emits `EkpSessionAuthenticated` / `Updated` / `Expired` / `LoggedOut`, re-auths silently via `POST auth/token/recover`: single-flight, retries the failed request once, keeps the session on a network failure, and drops a recovery that ends after the session was ended or replaced. `AuthInterceptor` exempts the token endpoint by path.
- The host supplies `TokenStore` and `EkpDeviceIdentity`; no platform code in the package.

Read `packages/ekp_api/README.md` and `packages/ekp_crypto/README.md` (protocol, RSA key rotation) before changing auth, cookies or the encrypted endpoints.

### App (`lib/`)

`core/` (api, crypto, platform, providers, router, theme, widgets) and `features/<name>/{screens,providers,widgets,models,utils,constants,services}/`. Riverpod 3 with hand-written providers (no `riverpod_generator`); `go_router`.

Material widgets come from `package:material_ui/material_ui.dart`, not `package:flutter/material.dart`: go_router 18 only recognises its `MaterialApp` and otherwise silently drops page transitions and the iOS back swipe. For the same reason `MobileKkmApp` uses `material_ui`'s `GlobalMaterialLocalizations.delegates`, not `AppLocalizations.localizationsDelegates`.

- **Injection seam:** `deviceIdentityProvider`, `tokenStoreProvider`, `userDataCacheProvider`, `lastPaymentMethodStoreProvider`, `appDatabaseProvider`, `dictionaryCacheProvider`, `aztecKeyStoreProvider`, `packageInfoProvider` throw by default and are overridden in `main()`; `ekpClientProvider` builds the client from them. Platform side effects are providers too, for tests: `urlOpenerProvider`, `linkSettingsProvider`, `appVersionProvider`, `photoCacheProvider`, `mapViewProvider`, `locationServiceProvider`, `photoPickerProvider`, `screenSecurityProvider`, `scanDisplayProvider`, `paymentBrowserProvider`. The profile photo is public (no token), loaded with `cached_network_image` behind `PhotoCache`, wiped on sign-out.
- **Aztec key:** the operator can rotate the RSA key, so it comes from the relay (sibling aztec-key-relay project, `AztecKeyRelay.address`) instead of Firebase. `AztecKeyController` (`core/providers/aztec_key_provider.dart`): bundled key → stored key (`aztec_key.json`, app support dir) → relay, asked once per run, only signed in and after start-up (never behind the splash). No answer, or a key that isn't RSA-2048, changes nothing. When the server refuses an encrypted call (in `guard()`), the relay's `refresh` is asked (≤ once a minute) and the request repeated once, only if the key changed. `AztecKeyRelay` (`core/crypto/`) has its own `Dio`: no device headers or token. Its `User-Agent` must be `mobileKKM/<version>` (`aztecKeyRelayProvider`): Cloudflare blocks anything else. The client reads the key per request from `aztecKeyInUseProvider`, a plain holder the controller writes to — not from the controller (it depends on the session, hence on the client) and not watched (that would rebuild the client and replay the splash).
- **Auth:** `AuthController` mirrors the session stream into `AuthStatus` (`unknown` → `authenticated` / `unauthenticated`), renewing an expired stored session first (10 s cap). `SignOutReason` (`sessionExpired`, `userDataFailed`) feeds the login screen's banner.
- **Start-up and app mode:** `appStartupProvider` runs behind the splash: `service-status`, then the config (8 s cap). `appStatusProvider` holds `AppMode`: `offline` (unreachable, config skipped), `unavailable` (`isAvailable: false`, the server's message; config still loaded), `outdated` (`minAppVersion` above `EkpDefaults.clientVersion`, `MobileAppConfig.supportsClient()`), else `online`. Only `outdated` blocks: `redirectFor(..., outdated: true)` → `UpdateRequiredScreen`. The splash waits for exactly this and the session; load nothing else behind it. After it, `account/user-data`, `mkkm/tickets/list` and the relay key go independently (no user data at all when outdated). Screens show stored data; `AppStatusBanner` reports the mode, always below the app bar (pinned above the list on Tickets, first scrolling item on Home and ticket details). Offline it adds when the tickets were stored (`ticketsSyncedAtProvider`, with the date if not today); unavailable shows the server's message alone. `mobileAppConfigProvider` loads once per run; only a failure is retried (`AppStatusController.check()`).
- **Routing:** the pure `redirectFor(uri, status)` (`core/router/app_router.dart`) holds all gating: `unknown` → splash, `authenticated` → home unless `Routes.isSignedIn`, `unauthenticated` → login unless `Routes.isPublic`. Register every new screen in one of the two. Signed in, a `CardGate` other than `open` sends signed-in paths to `/card-setup` (except `/account/delete` while `detached`), and an open gate sends set-up paths Home. `routerProvider` re-runs on `AuthStatus`, start-up and `cardGateProvider`. The four sections are `StatefulShellRoute.indexedStack` branches (`MainShell`); other signed-in screens are top-level routes above the navigation bar.
- **Ticket store:** mobile tickets live in drift (`core/database/app_database.dart`, schema 2, table `Tickets`: query columns, the `MkkmTicket` JSON as `payload`, `pinned` for Home). Screens read only the database (`mkkmTicketsProvider`, `homeTicketProvider`). `mkkmTicketsProvider` is `storedTicketsProvider` (the rows as sent) with the processing overlay: a `pending` ticket with a row in `Payments` reads as `processing`. `TicketSyncController` (`features/tickets/services/ticket_sync.dart`, kept alive from `MobileKkmApp`) fetches once signed in, start-up done and `online` (not waiting for user data), on return to the foreground (≤ once a minute) and on pull-to-refresh; it empties the store on sign-out. The purchase history (`ticketHistoryProvider`) is live, not stored.
- **Ticket card and lists:** `MkkmTicketCard` is the one card of list, Home and details. Colour = what can be done here (`toneOf()`: valid / wait / action / over), label = phase; "calm" (tone only in tile, label, bar, button) everywhere but Home's valid ticket. What the ticket is comes from the dictionaries only (`ticketZone`, `ticketFare`, `ticketPeriod`, `ticketProduct`), never `productName`; a bar replaces the subtitle while they first load. `returned` counts as running until the end date the return left (`phaseOf`). The mobile list only knows `active`, `pending`, `returned`: an unpaid, cancelled purchase drops out and shows only in history and details as `transactionStateId` 5 (`isCancelledPurchase` → `cancelled: true`, `TicketPhase.cancelled`: grey, only "Buy again"). Prices are Polish in every language (`formatPrice`: `99,00 zł`). The stub is `TicketActions` via `actionOf()` (`utils/ticket_format.dart`), in the official order: assigned → ticket control (disabled before the start), `processing` → nothing, `pending` → continue / check payment, `canAssign` → assign, else a note that other devices hold it. List order is `listRankOf()`; the pin button puts one running or coming ticket this phone can show or assign on Home. History is rows by month; its state word is the app's own (`purchaseStateOf`: 9 completed, 5 cancelled), with no "returned" (the history reports a return as state 9). The two lists are a `SegmentedButton` in the app bar's bottom. First loads show `ticket_skeletons.dart` in a `SkeletonPulse`, never a spinner. `TicketsScreen` has its own `ScaffoldMessenger` so snackbars lift its FAB.
- **Ticket actions:** `TicketActionsController` (`services/ticket_actions.dart`) runs `assign-e` and `payments/check`, then refreshes the sync and open details. Assigning asks first (it takes one of the ticket's two device places); a running call keeps the button's colours, says so and ignores taps; a refusal is the server's message in an error snackbar. The state says which call runs per ticket (`TicketBusy`). Continue payment waits for the ticket details (`detailsForPayment()`; the button busy, Check payment off) and hands them to `TicketPayScreen` as `extra`, so 25b never opens half filled; a failure is a snackbar.
- **Purchase** (`features/purchase/`, design 25a–25e): no sales rule is hard-coded. `SalesRules` (`models/sales_rules.dart`, pure Dart) works everything out from `tickets/ticket-sales-configuration`: a type (`specialTransportLines`) admits the products (`ticketNumberOfLines`) and periods sharing its `isNetwork` / `isMetropolitan` flag, `priceListConfigurations` says which (kind, product, period) is sold; zones are three toggles mapped to the product covering exactly them (`…LineQty` ≥ 0); zones every product of a type covers are fixed (the discount: Strefa I); the Lines section appears where several products cover the zones, one chip per product (All lines, then by `sumLinesToSelection`), and Duration waits for exactly that many lines; zone notes are data (`UnsoldZonesNote`, `FareZonesNote`, `DiscountNote`), worded by `zoneNoteText()`; `reconcile()` drops only answers no longer valid; prefill maps inhabitant fares by the kind dictionary's `groupId`; `startBounds()`: tomorrow within the configuration, an extension from the day after the old ticket ends to 30 days later. The two configurations are "privileged" / "not privileged" (`hasCracovCardPrivilege`), never "resident". `salesConfigurationProvider` reuses an answer for 5 minutes (a timestamp, no timer: a pending timer fails every widget test) and forgets it at sign-out. `PurchaseFormController` / `priceProvider` (300 ms debounce, stale answers dropped; a `code` on a 200 is a refusal) are families on `PurchaseEntry` (`/buy`, `?extend=` / `?similar=` a transaction code). `BuyScreen` (25a) reveals each section once the one above is answered (`_Reveal`, instant with animations off and on a prefilled form) and scrolls along with it only as far as the new section's heading and first row, only if hidden, never while the user holds the list (the form is a non-lazy `SingleChildScrollView`, so a new section can be measured). The price bar cross-fades (150 ms); everything else uses platform motion. `CheckoutScreen` (25b, `/buy/pay` with a `CheckoutEntry` as `extra`, or `TicketPayScreen` at `/ticket/:transactionCode/pay` from "Continue payment"): `CheckoutController` buys once (`tickets/buy`), then pays (`tickets/pay`, `ignoreWarnings` `false`, `true` after the pay-again dialog); method tiles by tPay group id in a fixed order (`PaymentMethods.tileOrder`: BLIK 150, the wallet — Google Pay 166 on Android, Apple Pay 170 on iOS —, card 103, Visa Mobile 171), every other group in the bank sheet in the server's order; the last group in secure storage (`ekp.last_payment_group`, cleared at sign-out); leaving after a buy goes to Tickets.
- **Payment** (`services/payment_session.dart`): tPay opens through `PaymentBrowser` (`core/platform/`, channel `de.codebucket.mkkm/payment`, our own code: a Custom Tab from `MainActivity`, `PaymentReturnActivity` taking `https://ekp.mpk.krakow.pl/payment/{success,rejected}` and handing it to `MainActivity` as an extra so Flutter's deep linking never sees it; `ios/Runner/PaymentBrowser.swift`, `SFSafariViewController`, reports Done). `PaymentSessionController` (kept alive from `MobileKkmApp`): a return link posts `payments/result`; success marks the ticket in `Payments` (drift, only "payment made", like the official `ticket-pending` store) and ends on Tickets, rejection returns to Check and pay with a notice; the browser closing without one (Android: back in the app and no link within 1 s; iOS: Done or back in front) asks `payments/check` now, at 5 s and 10 s (`/payment`: Finishing, Checking, Not yet). A cold start's return link (`initialReturn`) is still reported. `PaymentWatcher` syncs every 10 s while marks exist and drops a mark once the ticket isn't `pending` ("ready" when `active`), gone after a sync, or an hour old (beyond the official client). Endings are said on Tickets through `purchaseNoticeProvider`, which `PurchaseNotices` shows in Tickets' own messenger. Unverified on devices: whether tPay's redirects reach the app link from Chrome, and whether `payments/result` is posted by anyone on iOS.
- **Ticket details** (`TicketDetailsScreen`, `/ticket/:transactionCode`, `ticketDetailProvider`, live): the card is there at once from `storedTicketProvider`; the rest waits: skeletons, a dashed panel with retry on failure, the same without a button offline (reloads when `online` again; pulling asks the server first). An unanswered request marks the app offline. "Manage" rows follow the server's flags; `timelineOf()` merges the three state lists. Return and line change open with `TicketSummaryPanel`.
  - `TicketReturnScreen` (`…/return`): a date within `returnDateBounds()`, the server's preview, a confirmation. A return that keeps nothing (ticket not started) ends on the Tickets list, as the server hides such a ticket for a while.
  - `TicketChangeLineScreen` (`…/change-line`, where `canChangeLineOf()` allows): one tile per entry in `lines` — never assume how many. A tile pushes `LineSearchScreen` (not a router route; pops a `TransportLine`; `LineSearchScreen.pick(max:)` picks several for a purchase and pops the list on Done), which searches `dictionary/transport-line` by prefix and disables lines the ticket will already have. Save sends every line with the picks in place (`linesAfter()`, `tickets.changeLine(lines:)`), each with the search's `second_zone`; no zone choice (the official "II strefa" checkbox sets a value nothing reads). Picking the own line again undoes a change. Ends on the details with a snackbar; a refusal is a banner under the summary. Only one-line tickets were ever captured.
- **Ticket control** (`TicketControlScreen`, `/ticket-control/:ticketGuid`): a `CodeScreen` with Ticket (`ticketScope` + zone), Fare, Valid until. The ring is the only timer: `codeLifetime` 90 s (server codes last two minutes, `codeValidity`, though the reply no longer says so), `error` in the last 15 s (`CodeRunning.lowSeconds`), figures only in the screen-reader label. The first code starts full, a renewed one sweeps in from empty (300 ms); the one-second tick restarts whenever a code is shown. Unlike the official client it stays open: the next contract is fetched `renewAhead` (10 s) early and takes over with a full lifetime from when shown; a prefetched code older than the 30 s gap (app in background) is replaced, not shown. A failed fetch drops the code for the reason and a retry; an unanswered one is sent twice more first (after 1 s, 2 s), since the first request after a return often uses a dead connection. While hidden (`AppLifecycleListener` `onHide` / `onShow`, not `inactive`) the timer stands and nothing is fetched (the OS may freeze the app); a fetch that ends meanwhile is kept. On return the code goes on by the clock, else the prefetched one (if fresh) or a new one; earlier failures are retried. The three ticket routes are top-level; `Routes.isSignedIn` matches them by prefix.
- **Code protection** (ticket control and the Karta Krakowska code): `ScreenSecurity` (`no_screenshot`, no native code of ours) blanks screenshots and recordings on both platforms; on iOS it shows the launch screen in the app switcher (image overlay, `NoScreenshotImage` from `tool/render_branding.sh`) and hides the code while recording. No overlay on Android: it clears `FLAG_SECURE` on pause before drawing its cover and Samsung's recents picture leaked the code, so Android keeps the flag (blank preview). The plugin persists its state, so `main()` resets it. `ScanDisplay` (`screen_brightness`, `wakelock_plus`) sets the app's own brightness to full (no permission; the user's level returns outside the app) and keeps the screen awake.
- **`CodeScreen`** (`core/widgets/code_screen/`): brand header down to the photo's middle (its bar stays), photo 128 dp (152 from 600 dp width), name, customer number, optional details slot, `CodeArea`. The code takes what is left, 176–340 dp; only at 176 does the body scroll (`_FillRest`, a render object). The owning screen publishes a `CodeState` through a `ValueNotifier` (`CodeLoading`, `CodeShown`, `CodeHidden` while iOS records, `CodeFailed`, `codeProblem()`); a tap pushes `showEnlargedCode()`, a white route on the same notifier that closes when there is no code. `CodeRing` animates towards one second ahead (`leftNext`) and restarts every second from the true time, counted from `CodeRunning.since`, so it never hurries or jumps. Time is `clock.now()` (`package:clock`), faked by `flutter_test`: tests with a code up use `pumpWithCode()`, never `pumpAndSettle`.
- **Karta Krakowska** (`features/city_card/`): `CityCardScreen` (`/karta-krakowska`) reads the stored user data, not `account/inhabitant-status` (they agree): `mkkmData.hasInhabitantPrivilege` alone decides. True: "Active", the dates as sent (never compared with today), customer number, "Show status code". Else: the no-status card linking `Contacts.cityCardHowToUri`, no code. Opening and pulling reload the user data; offline the button is off with the reason. `CityCardCodeScreen` (`…/code`) calls `account/inhabitant-contract` without checks and shows the server's PNG until `expirationDate` (~5 min; `maxLifetime` when missing, past or too far, i.e. a wrong device clock), then closes back. A refusal was never captured: handle both a `message` without a picture and an HTTP error.
- **Account** (`features/account/screens/`, top-level routes framed by `AuthPage`): buttons off unless `online`, `AppStatusBanner` says why.
  - `EditAccountScreen` (`/account/edit`): two saves for two requests. The photo saves alone (`choosePhoto()` in `widgets/photo_source_sheet.dart`, shared with the card set-up → `account/photo`, photo cache cleared). Name, phone and address go in one `account/user-data` with every field, as the official client sends it (empty flat `""`, phone as bare digits). Save is off until a field differs; "Required" shows on the tap; user data reloads after either save. The address (`AddressFields`, shared) is always required. PESEL, birth date and e-mail are text. Leaving with changes asks (`PopScope`); offline the strip uses `offlineDetail`.
  - `ChangePasswordScreen` (`/account/change-password`): `auth/change-password`, checklist from `passwordPolicyProvider`, mismatch shown once the repeat field is left; ends on Account with a snackbar, session kept, leaving asks nothing (unlike the design's note). A refusal is HTTP 400 with a message (wrong password and `PasswordInHistory` captured).
  - `DeleteAccountScreen` (`/account/delete`, design 10e): `storage-medium/list` first; any card, mKKM included, leads to the website (`customerPageUrl`) as in the official client; only an empty list gets the password dialog and `PUT account/anonymise`, then the server's message and `AuthController.signOutLocally()` (no `auth/logout`: the token is dead). A wrong password is HTTP 400, its message under the field. Known gap: every signed-in user has an mKKM card and detaching it shuts the card gate, so the password step can't be reached in the app. `redirectFor` lets `/account/delete` past a `detached` gate only (`TODO(card-gate)`), but nothing leads there yet; the fix is to move the re-attach out of the gate. Captures show it would work: after a website detach, `storage-medium/list` is empty, `mkkmData` keeps `detached: true` and the customer code (`cardsNotAdded: true`), and the deletion went through.
- **Card set-up** (`features/card_setup/`): every signed-in screen assumes an attached mKKM card, so the set-up replaces the app until there is one. `cardGateOf()` (`models/card_gate.dart`) on the user data: `mkkmData == null` → `setUp`, `detached: true` → `detached`, else `open`; without user data `checking`, never `open` — it opens and closes only on what the server said. The first load (after sign-in, or a start without a stored copy) is waited for in place: sign-in button busy, or the splash ("Loading your account…" after 3 s). If it fails or exceeds 8 s (`UserDataController.firstLoadLimit`; the client has no request timeout), the user is signed out locally (`AuthController.signOutAfterUserDataFailed()`, no request), e-mail kept, the login says why. A stored copy never causes a sign-out; a failed refresh keeps it. (The design's "open Home after 8 s" was dropped.) Screens: `CardSetupScreen` (`/card-setup`, welcome or detached card), `CardAddressScreen` (`…/address`), `CardPhotoScreen` (`…/address/photo`), nested so back works. As in the official client the address goes only in `storage-medium/create-mkkm`, after `account/photo` (only for a newly picked photo: JPG, PNG or WebP ≤ 5 MB, `photoTypeOf()`). A refused `create-mkkm` returns to step 1 with the message. A detached card is re-attached with `storage-medium/create` and its customer code. The server makes the card after answering, so `CardSetupController` reloads the user data at once and every 3 s (`CardSetupStage.waiting` keeps the button busy; then `ready`; the design's "Creating…" screen was dropped); the gate stays shut (`settling`) until "Go to Home". Nothing is stored: a restart begins from the server. The street is free text; `StreetField` only suggests via `account/street-autocomplete` (`cityId` 15). Requests with a body-less success use `ResponseType.plain`; `EkpApiException.fromDio` still decodes their error body.
- **User data:** `userDataProvider` is keyed on `AuthStatus`: the cached copy at once, revalidated in the background, cleared on sign-out; without a cache the load is the first one and its failure ends the session. An answer is stored only for the session that asked (`_stillFor()`): take the `ref` before the request, as `ref.mounted` after an `await` in a notifier sees the latest build and misses a sign-out.
- **Dictionaries** (`ticketKindsProvider`, `ticketLineScopesProvider`, `ticketPeriodsProvider`, `cityCardTypesProvider` in `core/providers/dictionary_providers.dart`): one JSON file each via `FileDictionaryCache` (`core/dictionaries/`). The server sends `no-cache` without `ETag` / `Last-Modified`, so the rule is the app's (`DictionaryController.maxAge`, 24 h): a fresh copy as is, a stale one returned and replaced in the background, only a missing one waits or fails. Lazy, requested only signed in and after start-up, kept across sign-out. `transport-line` is a search, not stored. A new dictionary = a `Dictionary` constant + its provider.
- **Map** (`features/map/`): `MapScreen` puts a search placeholder over `mapViewProvider`'s `TransitMap` (`maplibre_gl`, OpenFreeMap styles via `MapDefaults`, light / dark, no API key). The native view exists only once the tab was opened. The screen drives it through `MapViewController`, never MapLibre directly. The location button asks permission on tap (`LocationService`, `geolocator`), then shows, moves to and tracks the position until the user drags; with an earlier permission it does so on opening. No compass (rotation, tilt off); attribution hidden, the (i) button shows `MapCredits`. The filter button is a placeholder. A surface-colour fade keeps the status bar readable.
- **Debug menu** (`DebugScreen`, `/debug`, `features/debug/`): 11 taps on Account's version line or the login logo (`DebugMenuTrigger`), release builds too; `redirectFor` allows it in both auth states. It changes real values. `DeviceIdentityController.change()` stores the ID under its usual key and the name under `ekp.device_name` (`saveDeviceIdentity`; an empty name restores the hardware's), which rebuilds `ekpClientProvider` (one splash pass, stored session). `screenSecurityEnabledProvider` turns code protection off until the app closes (deliberately not stored); while off, `screenSecurityProvider` hands out `NoScreenSecurity`, picked up the next time ticket control opens. It also shows the key's source and asks the relay again.
- **E-mail links:** activation / reset links are `https://ekp.mpk.krakow.pl/konto-uzytkownika/{activate|reset},<token>.html`, a domain the app can't verify. `EmailLink.tryParse` + `redirectFor` map them to `/activate/:token` / `/reset-password/:token`, reachable in every auth state. Android: an unverified intent filter, and `LinkSettings` uses the `de.codebucket.mkkm/links` channel to `MainActivity` to check / open "Open supported links". iOS always opens them in the browser.
- **Password managers:** a login e-mail beside a password (sign-in, registration) has `[AutofillHints.username, AutofillHints.email]`, `username` first (iOS reads only the first); an e-mail without a password has `email` alone. New passwords are `newPassword`; a saving form calls `TextInput.finishAutofillContext()` once the server took it. Change password and the deletion dialog have no login field (a hidden one was decided against); the dialog's group is `AutofillContextAction.cancel`. iOS has no Associated Domain (not our domain), hence no strong-password suggestion.
- **Orientation:** portrait only, tablets too: `SystemChrome.setPreferredOrientations` in `main()`, `screenOrientation="portrait"` on `MainActivity`, `UISupportedInterfaceOrientations` + `UIRequiresFullScreen` in `Info.plist` (iPad multitasking would force rotation). Android 16 ignores the lock on large screens.
- **Minors:** as in the official client, under 16 (`isUnder16`, from PESEL or the date) never goes to `auth/register`; `websiteRegistrationUri()` opens the website's form (`customerPageUrl` + `auth/register?…`) with what was typed.
- **Errors:** UI text for a failed call goes through `describeError()` (`core/api/error_messages.dart`); server messages are shown verbatim (always Polish).
- **l10n:** `lib/l10n/app_en.arb` is the template, `app_pl.arb` the translation; add to both. `AppLocalizations.of(context)` is non-nullable.

### App tests

`pumpApp()` (`test/support/harness.dart`) pumps the real `MobileKkmApp`: a real `EkpClient` over `FakeAdapter` (replies keyed by method + path suffix, unmatched → 404), `InMemoryTokenStore`, platform fakes. `session: signedInSession` starts signed in. Assert on `adapter.requests` / `requestTo()` and `app.router`; use `tapVisible()` and `field(label)` for forms.

- The harness owns the `ProviderContainer` (`UncontrolledProviderScope`) and an in-memory drift database per test (disposing with the widget tree would cancel drift's stream queries and leave a pending timer). `database:` seeds one or keeps it across two `pumpApp` calls; `settle: false` keeps the splash up; `tall: true` for a whole lazy list (the test font is wide).
- A 404 counts as "online, no config" at start-up. Only `account/user-data` has a default reply (`FakeAdapter.fallback`: an account with a card), since a signed-in app without user data signs out; a test about it uses `fail`, `hold` or `reply`.
- A test resting on a held first load disables animations (`FakeAccessibilityFeatures(disableAnimations: true)`), since the skeleton pulse never settles; Home's placeholder progress bar never does either, so leave Home with `pump`.
- Helpers: `openTab()`, `pullToRefresh()`, `app.location`; `photoPicker:` (`FakePhotoPicker`, `onePixelPng`); `app.screen` (`FakeScreenSecurity`, plays a recording); `app.scanDisplay` (`FakeScanDisplay`); `app.container` for providers no screen shows; `dictionaryCache:` (`InMemoryDictionaryCache`); `app.relay`, a second `FakeAdapter` with relative paths (`aztec-key`), seeded with `relay:` (no reply → bundled key); `aztecKeyStore:` (`InMemoryAztecKeyStore`); map: `fakeMapKey`, `FakeMapView` (`app.map`), `pumpApp(location:)` with `FakeLocationService`; debug identity changes show only in `app.savedIdentities` and the provider state (the client is fixed).

The ticket control test reads the synthetic contract from `packages/ekp_api/test/fixtures/`.

## Design

The design handoff (round 1) lives in `AppTheme` (`lib/core/theme/app_theme.dart`) and `lib/core/widgets/`; screens style through them, not locally. `AppTheme`: fidelity scheme of `#303F9F` with pinned roles, `primaryContainer` = brand in both themes, `AppColors` (success), splash colours (each theme's surface; also in `pubspec.yaml` and `tool/render_branding.sh`), Montserrat (display / headline / title) + Inter (body / label), 56 dp pill buttons, 64 dp app bar, radius-16 outlined fields, radius-28 cards, dialogs and sheets.

- `RowGroup` / `GroupRow` + `IconTile`: every list of rows.
- `MessageBanner` (error / success / info, optional action; with `actionIcon` a tonal button under the text): server messages verbatim, top of a form.
- Filter chips (`FilterChip`) are themed in `AppTheme.chipTheme`: M3 geometry, radius 8, secondaryContainer when selected. `AppStatusBanner`: the compact offline / unavailable strip; `offlineDetail` replaces "Showing saved data." where the screen shows typed input.
- `FormCard` only for multi-section forms; one group of fields sits on the surface. `LeadHeader` opens lead screens (`LeadHeader.waiting` for every screen waiting on the server: activation, payment status); `AuthPage` frames them with an optional pinned button.
- `CheckRow` for a checkbox with its label (level with the fields, whole row toggles), not `Checkbox` / `CheckboxListTile`.
- `SystemBarScrim` around content that scrolls under the system navigation bar (ticket details), not a `SafeArea`; not for screens ending in their own bar or button.
- `BottomActionBar` for a pinned bottom button: 12 dp gaps with the system inset added (not `SafeArea(minimum:)`, which leaves no gap).
- `PhotoPreview`: the round photo above photo buttons, fixed size, ring for a picked photo, shown once decoded. Edit account keeps its saved photo on screen so the cleared cache doesn't flash the initials.
- `BulletCard` for a few points before going on; `Perforation` for the tear-off line.
- `CodeScreen` for any code shown to someone else, not a screen's own ring or panel.
- `EmptyStateCard` (`quiet` inside a screen) for missing or failed content, `LoadProblem` inside a sheet or form, `SkeletonBox` in a `SkeletonPulse` for first loads (no centred spinners), `StatusChip` (icon + word, never colour alone).
- `showAppSnackBar()` for every snackbar: plain, `success`, `error` (6 s, closable). Busy buttons: `SubmitButton` (takes a `style`), 18 dp spinner, 2 dp stroke, foreground colour, label says what it's doing.
- On the brand surface use `primaryFixed` / `onPrimaryFixed`, never `primary` (equal to `primaryContainer` in light).
- Filled buttons in dialogs use `AppTheme.dialogAction` (40 dp); the global minimum is 56.

## Conventions

- Icons: `Symbols.<name>_rounded` (`package:material_symbols_icons/symbols.dart`), not `Icons.*`; outlined by default, `fill: 1` for filled.
- App imports are `package:mobile_kkm/...` (`always_use_package_imports`); packages use relative imports in `lib/src/`.
- Keep `dart format` and `dart analyze` clean. Generated files are excluded from analysis, not from formatting.
- `riverpod_lint` runs as an analyzer plugin, app only. Shared lints and the formatter width are in `analysis_options_shared.yaml`; Flutter-only rules in the root file. `always_put_control_body_on_new_line`: every control body needs braces. `discarded_futures`: wrap fire-and-forget calls in `unawaited(...)`.
- Conventional Commits with a member scope: `feat(app): …`, `fix(ekp_api): …`, `chore: …`.
