# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

mobileKKM: an unofficial, GPL-3.0 Flutter client (Android + iOS) for the mKKM / EKP ticketing backend of ZTP / MPK Kraków, reverse-engineered from the official Android app. The repo is a [pub workspace](https://dart.dev/tools/pub/workspaces) with three members:

- `.` (`mobile_kkm`) — the Flutter app. So far: theme, splash, the signed-out flows (login, registration, password reset, e-mail link handling), the mKKM card set-up that a signed-in account without a card gets in the app's place, and the signed-in shell with its four sections (Home, Tickets, Map, Account). A hidden debug menu sits behind the version line on Account and the logo on the login screen. The Map section is a MapLibre map of Kraków with a search-bar placeholder and a button for the user's position; vehicles, stops with live departures and stop search are not built yet. The Tickets section has the ticket's details, its return, changing its line and the ticket control screen (AZTEC code). Karta Krakowska (from Account and Home) has its status and its status code. Account has Edit account, Change password and Delete account. Noticing by itself that the connection is back is not built either: the server is only asked again at start-up and on pull-to-refresh (a `connectivity_plus` listener that calls `AppStatusController.check()` is the planned improvement). Also not built yet, and routed to `ComingSoonScreen`: the purchase flow (`/buy`, opened from the floating button on Tickets and from Home, and from a pending ticket's "Continue payment" and the details' "Extend" / "Buy similar"), the 5+1 subscription.
- `packages/ekp_api` — pure-Dart `dio` client for the EKP backend. No Flutter dependency.
- `packages/ekp_crypto` — pure-Dart crypto for the encrypted `assign-e` / `contract-e` endpoints (RSA-wrapped requests, AES-128-CBC contract decryption → AZTEC token).

Dependency direction: app → `ekp_api` → `ekp_crypto`.

The look comes from a design handoff (round 1: tokens, ticket card, Home, Tickets, ticket control, Account, the signed-out screens); what it fixed is in `AppTheme` and the shared widgets under `lib/core/widgets/`, see "Design" below. Of its screens only the first-start notice (11h) is still to be done.

`docs/official-app/` describes the official client's screens and flows (navigation, every button's rule, the request behind each step), reconstructed from its decompiled bundle in `.dumps/react/`. Read the relevant document before building a feature the official app already has; its README has a module map for finding the original code.

Android release builds (application ID `de.codebucket.mkkm`):

```bash
flutter build apk --release                            # universal APK for direct download; not --split-per-abi, which
                                                       # adds 1000 × ABI to the version code and puts it above Play's
flutter build appbundle --release                      # .aab for Google Play
```

Either build takes `--dart-define=AZTEC_KEY_RELAY_URL=https://relay.example.org` to use another instance of the aztec key relay than `relay.mobilekkm.app` (the address without a path; `flutter run` takes it too), and `--dart-define=AZTEC_KEY_RELAY_TOKEN=…` when that instance has a `RELAY_API_TOKEN` set. The token can be read out of the built app.

The release key is read from `android/key.properties` (gitignored: `storeFile`, `storePassword`, `keyAlias`, `keyPassword`). Without that file the release build falls back to the debug key, so it builds anywhere but must not be published. Raise the `+N` of `version:` in `pubspec.yaml` for every upload.

## Privacy constraints

- `.dumps/` holds raw network captures with real credentials and personal data. It is gitignored; never commit it, and never copy values from it into fixtures, tests, docs or commit messages.
- Fixtures in `packages/ekp_api/test/fixtures/` are sanitized. Keep new ones synthetic/scrubbed. `packages/ekp_api/tool/` (fixture extraction) is deliberately gitignored and maintainer-local.
- `ekp_crypto` tests use synthetic vectors only; `packages/ekp_crypto/tool/make_synthetic_contract.dart` regenerates the synthetic contract fixture used by `ekp_api`'s tests.

## Architecture

### `ekp_api`

- `EkpClient` (`lib/src/ekp_client.dart`) is the facade: it builds one `Dio` pipeline (cookie jar → `DeviceHeadersInterceptor` → `AuthInterceptor`) and exposes one API object per domain (`auth`, `account`, `tickets`, `payments`, `subscriptions`, `dictionaries`, `storageMediums`, `invoices`, `misc`). Each domain lives in `lib/src/<domain>/` as `<domain>_api.dart` + `<domain>_models.dart`.
- API classes extend `EkpApiService` and wrap calls in `guard()`, which converts `DioException` into the sealed `EkpApiException` hierarchy (`EkpNetworkException`, `EkpUnauthorizedException`, `EkpHttpException`, `EkpSessionExpiredException`). Callers never see `DioException`.
- Request bodies are built as explicit maps inside the typed service methods; response models are `freezed` + `json_serializable` and mirror the observed wire format exactly, inconsistencies included (e.g. `code` is `Object?` because it is numeric on some endpoints and a string on others). Don't "tidy" models away from the wire format.
- `EkpSessionManager` owns the session: persistence through the host-supplied `TokenStore`, a lifecycle event stream (`EkpSessionAuthenticated` / `Updated` / `Expired` / `LoggedOut`), and silent re-auth via `POST auth/token/recover`. Recovery is single-flight, retries the failed request once, and a network failure during recovery keeps the session rather than expiring it. The token endpoint is exempted from Bearer injection and recovery by path in `AuthInterceptor`.
- The host supplies `TokenStore` and `EkpDeviceIdentity`; the package itself stays free of platform code.

Design rationale and the reverse-engineered protocol details are in `packages/ekp_api/README.md` and `packages/ekp_crypto/README.md` (including the RSA key rotation procedure) — read them before changing auth, cookies or the encrypted endpoints.

### App (`lib/`)

Layout: `core/` for shared code (api, crypto, platform, providers, router, theme, widgets) and `features/<name>/` split by kind (`screens/`, `providers/`, `widgets/`, `models/`, `utils/`, `constants/`, `services/`).

State is Riverpod 3 with hand-written providers (no `riverpod_generator`); routing is `go_router`.

Material widgets come from `package:material_ui/material_ui.dart`, not `package:flutter/material.dart`: go_router 18 only recognises `material_ui`'s `MaterialApp` and silently drops page transitions and the iOS back swipe otherwise. For the same reason `MobileKkmApp` uses `GlobalMaterialLocalizations.delegates` from `material_ui` rather than the generated `AppLocalizations.localizationsDelegates`.

- **Injection seam:** `deviceIdentityProvider`, `tokenStoreProvider`, `userDataCacheProvider`, `appDatabaseProvider`, `dictionaryCacheProvider`, `aztecKeyStoreProvider` and `packageInfoProvider` throw by default and are overridden in `main()` (`flutter_secure_storage`-backed implementations, the drift database, and JSON files in the application support directory). `ekpClientProvider` builds the `EkpClient` from them. Platform side effects are also providers (`urlOpenerProvider`, `linkSettingsProvider`, `appVersionProvider`, `photoCacheProvider`, `mapViewProvider`, `locationServiceProvider`, `photoPickerProvider`, `screenSecurityProvider`, `scanDisplayProvider`) so tests can replace them. The profile photo is public (no token): it is loaded with `cached_network_image` behind `PhotoCache` and wiped on sign-out.
- **Aztec key:** the RSA key for `assign-e` / `contract-e` can be rotated by the operator, so the app gets it from the relay at `relay.mobilekkm.app` (the sibling aztec-key-relay project; `AztecKeyRelay.address`, replaceable at build time with `AZTEC_KEY_RELAY_URL`, with `AZTEC_KEY_RELAY_TOKEN` sent as a Bearer token when set) instead of Firebase. `AztecKeyController` (`core/providers/aztec_key_provider.dart`) starts with the key bundled in `ekp_crypto`, then the one stored from an earlier run (`aztec_key.json` in the application support directory), and asks the relay once per run: only when signed in and after start-up, never behind the splash. A relay that does not answer, or a key that is not RSA with 2048 bits, changes nothing. Both encrypted calls go through `guard()`: when the server refuses one (a reply that says no, or an HTTP error; what a wrong key looks like is not known), the relay's `refresh` is asked, at most once a minute, and the request is repeated once only if the key turned out to be another. `AztecKeyRelay` (`core/crypto/`, with the `AztecKey` model and its store) has a `Dio` of its own: no device headers and no token go to the relay. Every request to it carries the `User-Agent` the relay was built with, `mobileKKM/<version>`, put together in `aztecKeyRelayProvider` from `packageInfoProvider`: Cloudflare in front of the relay blocks anything that does not start with `mobileKKM`. The client reads the key per request from `aztecKeyInUseProvider`, a plain holder the controller writes to; not from the controller, which depends on the session and so on the client, and not as a watched value, which would rebuild the client and send the app through the splash. The debug menu shows where the key is from and asks the relay again.
- **Auth state:** `AuthController` mirrors `EkpSessionManager`'s event stream into `AuthStatus` (`unknown` → `authenticated` / `unauthenticated`). On startup it renews an expired stored session (10 s cap) before leaving `unknown`. `AuthState` also says why the user was signed out, for the login screen's banner (`SignOutReason`): `sessionExpired`, or `userDataFailed` (see the card set-up).
- **Start-up and app mode:** `appStartupProvider` (`core/providers/app_startup_provider.dart`) runs behind the splash: `service-status`, then the app config (8 s cap). `appStatusProvider` holds the result as `AppMode`: `offline` when the server is unreachable (config skipped), `unavailable` with the server's message when it reports `isAvailable: false` (config still loaded, as in the official client), `outdated` when the config's `minAppVersion` is above `EkpDefaults.clientVersion` (`MobileAppConfig.supportsClient()`), else `online`. `outdated` is the one blocking state: `redirectFor(..., outdated: true)` sends everything to `UpdateRequiredScreen`. The splash waits for exactly this and the session (read, and renewed if expired); nothing else may be loaded behind it. Request order at start: `service-status` → config → `account/user-data`, `mkkm/tickets/list` and the relay's key, the last three independently of each other; `UserDataController` does not ask the server before start-up is through, or at all when outdated. Nothing blocks the UI: `AppStatusBanner` reports the mode and the screens show stored data. The strip goes below a screen's app bar, never into it: pinned between the bar and the list on Tickets, the first scrolling item on Home and ticket details. Offline it is two lines, the second saying when the tickets were last stored (`ticketsSyncedAtProvider`; with the date when that was an earlier day); for a switched-off service it is the server's message alone. `mobileAppConfigProvider` is loaded once per run; only a failed load is repeated (`AppStatusController.check()`).
- **Routing:** `routerProvider` re-runs its redirect whenever `AuthStatus` changes or start-up finishes; until then it passes `AuthStatus.unknown`. The pure function `redirectFor(uri, status)` in `core/router/app_router.dart` holds all the gating logic: `unknown` → splash, `authenticated` → home unless `Routes.isSignedIn`, `unauthenticated` → login unless `Routes.isPublic`. A new signed-out screen must be added to `Routes.isPublic`, a new signed-in one to `Routes.isSignedIn`. While authenticated, `redirectFor` also takes the `CardGate` (below): anything but `open` sends every signed-in path to `/card-setup` (but for `/account/delete` while `detached`, for now), and an open gate sends the set-up's paths Home; the router re-runs on `cardGateProvider` too. The four sections are branches of a `StatefulShellRoute.indexedStack` (`MainShell`); other signed-in screens are top-level routes above the navigation bar.
- **Tickets:** the mobile tickets (`mkkm/tickets/list`) live in a drift database (`core/database/app_database.dart`, table `Tickets`: a few query columns plus the `MkkmTicket` JSON as `payload`, and the user's home-screen `pinned` flag). Screens read only the database (`mkkmTicketsProvider`, `homeTicketProvider`); `TicketSyncController` (`features/tickets/services/ticket_sync.dart`) fills it, and only asks for the list once the user is signed in, start-up is through and the mode is `online` (it does not wait for the user data): as soon as those hold, on return to the foreground (at most once a minute) and on pull-to-refresh. It empties the store on sign-out. It is kept alive from `MobileKkmApp` for that reason. The purchase history (`ticketHistoryProvider`) is a live request and is not stored.
- **Ticket screens:** `MkkmTicketCard` (a `TicketCard` for a mobile ticket) is the one card of the list, Home and the details. Its colour says what can be done with the ticket here (`toneOf()`: valid / wait / action / over), its label which phase it is in; everywhere but on Home's valid ticket the card is "calm" (neutral, the tone only in the icon tile, label, bar and button). What the ticket is comes from the dictionaries alone, the same in the list and the details: zone (`ticketZone`), fare (`ticketFare`) and period (`ticketPeriod`, together `ticketProduct`); the server's `productName` only comes with a ticket's details and is not used for mobile tickets. A `returned` ticket is treated as running until the end date the return left it with (`phaseOf`). A purchase cancelled for want of a payment never shows in the mobile list: the list knows only `active`, `pending` and `returned`, and an unpaid ticket drops out of it. Only the history and the details say so, with `transactionStateId` 5 (`isCancelledPurchase`); the details then pass `cancelled: true` to the card (`TicketPhase.cancelled`: grey, the reason on its stub) and offer only "Buy again". Prices are written the Polish way in every language (`formatPrice`: `99,00 zł`). While the fare and period dictionaries are on their way for the first time, the card shows a bar in the subtitle's place. The stub under the perforation is `TicketActions`, chosen by `actionOf()` in `utils/ticket_format.dart` in the official client's order: assigned → ticket control (disabled before the start), `processing` → nothing to do, `pending` → continue / check payment, `canAssign` → assign to this device, otherwise a note that other devices hold it. The Tickets list is in the order of `listRankOf()`, and its pin button puts one ticket on Home (only a running or coming ticket this phone can show or be assigned has one); the purchase history is rows by month, not cards. The two lists are the halves of a `SegmentedButton` in the app bar's bottom. A first load shows pulsing shapes of what is coming (`ticket_skeletons.dart` inside a `SkeletonPulse`), never a spinner. `TicketsScreen` has a `ScaffoldMessenger` of its own, so that its snackbars lift its floating button instead of covering it from the shell's scaffold. A row says what became of the purchase in a word of the app's own (`purchaseStateOf`: completed or cancelled, by `transactionStateId` 9 or 5), not in the server's sentence. There is no "returned" there: the history reports a returned ticket like any other that went through (state 9, no period code), so only its details show the return. `TicketActionsController` (`services/ticket_actions.dart`) runs `assign-e` and `payments/check` and then refreshes the sync and the open details. Assigning asks first (it takes one of the ticket's two device places); while a call runs its button keeps its colours, says so and ignores taps; a refusal is the server's message in an error snackbar, not a banner. A card opens `TicketDetailsScreen` (`/ticket/:transactionCode`, `ticketDetailProvider`, a live request; its "Manage" rows follow the server's flags, and `timelineOf()` merges the three state lists). The card is there at once from the stored list (`storedTicketProvider`); only what is under it waits for the request: shapes while it loads, a dashed panel with a retry when it failed, and offline the same panel without a button (the details reload when the mode is `online` again, and pulling down asks the server first). A request without an answer marks the app offline, as the ticket sync does. The return and the line change open with `TicketSummaryPanel`, the indigo line that says which ticket they are about. From there the way goes on to `TicketReturnScreen` (`…/return`: a date within `returnDateBounds()`, the server's preview, then the return behind a confirmation; a return that keeps nothing, of a ticket still to start, ends on the Tickets list, because the server drops such a ticket from its lists for a while). `TicketChangeLineScreen` (`…/change-line`, only where `canChangeLineOf()` allows it) draws one tile per entry in the ticket's `lines`, never assuming how many: a tap pushes `LineSearchScreen` (not a route of the router: it pops with the picked `TransportLine`), which asks `dictionary/transport-line` by number prefix and shows the lines the ticket will already have as not to be picked. Save sends every line of the ticket with the picked ones in their places (`linesAfter()`, `tickets.changeLine(lines:)`); only one-line tickets were ever captured. Each line goes with the `second_zone` the search gave it, as in the official client, whose "II strefa" checkbox on a picked line sets a value nothing reads; so there is no zone choice here. Picking the ticket's own line again takes a change back. It ends on the details with a snackbar; a refusal is a banner under the summary sentence. `TicketControlScreen` (`/ticket-control/:ticketGuid`) is a `CodeScreen` (below) with the ticket's facts as a table in its details slot: Ticket (`ticketScope` with the zone), Fare, Valid until. The ring around the code is the only timer: it drains over `codeLifetime` (90 s: the server's codes are good for two minutes, but its reply no longer says so) and turns `error` in the last 15 s (`CodeRunning.lowSeconds`); there is no countdown in figures, only in the code's label for screen readers. Unlike the official client it stays open: the next contract is fetched `renewAhead` (10 s) before the end and takes over then with a whole `codeLifetime` of its own, counted from when it is shown, the ring full again at once. The gap between the 90 s and the server's two minutes (`codeValidity`) is what allows that; a fetched code that waited longer than the gap (the app was in the background) is not shown but replaced. Only if the fetch fails is the code dropped for the reason and a retry. While it is open `ScreenSecurity` (the `no_screenshot` plugin, no native code of our own) keeps screenshots and recordings empty on both platforms and shows the launch screen in the app switcher: the plugin's image overlay, whose full-screen covers (`NoScreenshotImage` in the iOS asset catalog, `drawable-nodpi/no_screenshot_image.png` and its `-night` twin on Android) come from `tool/render_branding.sh`. On iOS the code is also hidden in the app while a recording runs. The plugin persists its state, so `main()` resets it at start-up. Also unlike the official client, the display is at full brightness and kept awake while the screen is open (`ScanDisplay`, the `screen_brightness` and `wakelock_plus` plugins): the app's own brightness, not the system setting, so Android needs no permission and the user's level is back outside the app. The three routes are top-level, above the navigation bar; `Routes.isSignedIn` knows them by prefix.
- **Code screens:** `CodeScreen` (`core/widgets/code_screen/`) is the frame of Ticket control and of the Karta Krakowska code: the header in the brand colour down to the middle of the photo (its bar stays, the rest scrolls with the body), the photo at a fixed 128 dp (152 from 600 dp width), name and customer number, an optional details slot, and `CodeArea`. The code is what gives way: its side is what is left under the person, between 176 and 340 dp, and only at 176 does the body scroll (`_FillRest`, a render object, because the code lays itself out by the room it gets). The screen that owns the code publishes a `CodeState` through a `ValueNotifier` (`CodeLoading`, `CodeShown`, `CodeHidden` while iOS records the screen, `CodeFailed` with the server's message or the app's, `codeProblem()`); a tap on a shown code pushes `showEnlargedCode()`, a white route in both themes that listens to the same notifier, so it is the same code with the same timer, and closes by itself when there is no code to show. `CodeRing` moves a second per second, always on its way to where the time will be a second on (`leftNext`), so that it is empty when the time is. Every second it starts from where the time is rather than from where it stands, so a ring that stood still (under the enlarged code, or with the app in the background) is in place at once instead of hurrying there. That never settles: tests with a code up use the harness's `pumpWithCode()` instead of `pumpAndSettle`.
- **Karta Krakowska:** `features/city_card/`. `CityCardScreen` (`/karta-krakowska`) shows the status from the stored user data, not from `account/inhabitant-status` (the captures show the two agree): `mkkmData.hasInhabitantPrivilege` alone decides, as `isActive` does in the official client. True: the card with "Active", the dates as sent (never compared with today) and the customer number, and "Show status code". Anything else: the no-status card with a link to the city's page (`Contacts.cityCardHowToUri`), and no way to a code. Opening the screen and pulling down reload the user data; offline the button is off, with the reason. `CityCardCodeScreen` (`…/code`) asks `account/inhabitant-contract` without any check first and shows the PNG the server drew. The code is good until the reply's `expirationDate` (about 5 min; `maxLifetime` stands in when the date is missing, past or further off, i.e. the device clock is wrong). There is no next code: when the time is up the screen closes back to the status. A refusal was never captured, so both forms are read: a reply with `message` and no picture, or an HTTP error. Display and screenshot protection are as on Ticket control.
- **Account screens:** `features/account/screens/`, top-level routes framed by `AuthPage`. All three need the server: while the mode is not `online` their buttons are off and `AppStatusBanner` says why. `EditAccountScreen` (`/account/edit`) has two saves, as there are two requests. The photo is saved by itself under the picture (`choosePhoto()` in `widgets/photo_source_sheet.dart`, shared with the card set-up, then `account/photo`, the photo cache cleared). Name, phone and address go in one `account/user-data` request with every field, as the official client sends it (a flat that is left out as `""`, the phone as bare digits); Save is off until a field differs from the user data, "Required" shows on the tap, and the user data is reloaded after either save. The address (`AddressFields`, shared with the card set-up) is always required: every account that gets here has a card. PESEL, date of birth and e-mail are text, not fields. Leaving with unsaved changes asks first (`PopScope`); offline the strip takes `offlineDetail`, since what is on screen is typed, not stored. `ChangePasswordScreen` (`/account/change-password`): `auth/change-password`, the checklist from `passwordPolicyProvider`, the mismatch said once the repeat field was left; it ends on Account with a snackbar, the session stays, and unlike the design's note leaving asks nothing. A refusal is HTTP 400 with a message (a wrong current password and `PasswordInHistory` were captured). `DeleteAccountScreen` (`/account/delete`) is 10e as designed: `storage-medium/list` first, and any card, the mKKM card included, leads to the website (`customerPageUrl`) as in the official client; only an empty list gets the password dialog (filled by a password manager like any other, see "Password managers") and `PUT account/anonymise`. The server's message is shown, then `AuthController.signOutLocally()` ends the session without `auth/logout`, which the dead token would fail. A wrong password is HTTP 400 with the server's message, shown under the field. Known gap: every signed-in user has an mKKM card, and detaching it shuts the card gate, so the password step cannot be reached in the app today. `redirectFor` lets `/account/delete` past the gate of a detached card, and of that alone (marked `TODO(card-gate)`), but nothing on the set-up screens leads there yet; the way out is to move the re-attach out of the gate. The captures show it would work then: after a detach on the website `storage-medium/list` is empty while `account/user-data` keeps `mkkmData` with `detached: true` and the customer code (and `cardsNotAdded: true`), and the deletion went through from there.
- **E-mail deep links:** activation / reset links point at `https://ekp.mpk.krakow.pl/konto-uzytkownika/{activate|reset},<token>.html` — a domain the app cannot verify. `EmailLink.tryParse` recognises the path and `redirectFor` maps it to `/activate/:token` or `/reset-password/:token`, which are reachable in every auth state. Android has an unverified intent filter, and `LinkSettings` talks to `MainActivity` over the `de.codebucket.mkkm/links` method channel to check/open the per-app "Open supported links" setting; on iOS these links always open in the browser.
- **Map:** `features/map/`. `MapScreen` puts a search-bar placeholder over the view built by `mapViewProvider`: `TransitMap`, a `maplibre_gl` platform view with OpenFreeMap vector styles (`MapDefaults`, light and dark by theme; no API key). The branch is built on first visit, so the native view only exists once the tab was opened. The screen moves the map through a `MapViewController` that the view attaches to, so it never touches MapLibre itself. The location button asks for the permission on tap (`LocationService`, `geolocator`), then draws the position, moves there and follows it (MapLibre's tracking mode) until the user drags the map away; with the permission from an earlier run it does the same by itself when the tab is opened. The map has no compass (rotation and tilt are off) and its own attribution button is hidden; the (i) button on the screen lists the credits instead (`MapCredits`). The filter button above the location button (the one nearest the thumb) is a placeholder. A fade of the surface colour keeps the status bar readable over the map. Tests get a keyed `SizedBox` instead (`fakeMapKey`, `FakeMapView` as `app.map`, and `FakeLocationService` via `pumpApp(location:)` in the harness).
- **Debug menu:** `DebugScreen` (`/debug`, `features/debug/`), hidden: eleven taps on the version line of Account or on the logo of the login screen open it (`DebugMenuTrigger`), in release builds too. It needs no session: `redirectFor` lets it through in both auth states. It changes the real values, not a layer over them. `deviceIdentityProvider` is a notifier (`DeviceIdentityController`): `change()` stores the ID under its usual key and the name under `ekp.device_name` (`saveDeviceIdentity`; an empty name brings the hardware's back) and replaces the state, so `ekpClientProvider` is rebuilt and the app passes through the splash once with the stored session. `screenSecurityEnabledProvider` switches the ticket code's protection off until the app is closed; it is deliberately not stored. The ticket control screen knows nothing of it: while off, `screenSecurityProvider` hands out `NoScreenSecurity`, and the screen picks that up the next time it is opened. In the harness the client is fixed, so only `app.savedIdentities` and the provider's state show a change.
- **Card set-up:** `features/card_setup/`. Mobile tickets live on the mKKM card, and every signed-in screen assumes the account has an attached one, so the set-up stands in the app's place until it does. `cardGateProvider` (`cardGateOf()` in `models/card_gate.dart`) reads `account/user-data`: `mkkmData == null` → `setUp`, `detached: true` → `detached`, else `open`. It closes only on what the server said, and opens only on that too: without user data it is `checking`, never `open`. The first load (right after sign-in or on a start without a stored copy) is waited for where the user is, the sign-in screen with its button busy or the splash (which says "Loading your account…" after 3 s), so neither Home nor the set-up shows before it is known which. No user data means no session: when that first load fails, or takes more than 8 s (`UserDataController.firstLoadLimit`; the client has no request timeout), the user is signed out on this device (`AuthController.signOutAfterUserDataFailed()`, no request to the server, which may be the one not answering) and the login screen says so, with the e-mail kept. A stored copy is never the reason for a sign-out: a failed refresh keeps it in use. The design's "opens on Home after 8 s" was dropped for this. `CardSetupScreen` (`/card-setup`) is the welcome or the detached card; `CardAddressScreen` (`…/address`) and `CardPhotoScreen` (`…/address/photo`) are the two steps, child routes so that back works. As in the official client the address goes only inside `storage-medium/create-mkkm`, after `account/photo` (sent only when a new photo was picked; JPG, PNG or WebP up to 5 MB, told by `photoTypeOf()`). A refused `create-mkkm` leads back to step 1 with the server's message. A detached card is attached again with `storage-medium/create` and its customer code. The server makes the card after it has answered, so `CardSetupController` reloads the user data at once and then every 3 s until the card is there (`CardSetupStage`: `waiting` keeps the button that asked busy, for as long as it takes, `ready` is the result; the design's "Creating…" screen was dropped). The gate stays shut (`settling`) until the user taps "Go to Home". Nothing of this is stored: an app closed while waiting starts from what the server says. Unlike the official client the street is free text; `StreetField` only offers `account/street-autocomplete` (Kraków, `cityId` 15) as help. Requests whose success has no body are made with `ResponseType.plain`; `EkpApiException.fromDio` decodes their error body all the same, which is where the server's message comes from.
- **Password managers:** every e-mail field that is the login next to a password (sign-in, registration) has `[AutofillHints.username, AutofillHints.email]`, `username` first because iOS reads only the first hint; an e-mail without a password beside it (forgot password, a repeat e-mail) has `email` alone, which managers fill as the contact address. New passwords are `newPassword` (Android offers to generate one), and a form that saves calls `TextInput.finishAutofillContext()` once the server took it. Change password and the deletion dialog have no login field: with one login saved for the app a manager updates or fills that one. A hidden e-mail field, for users with several saved logins, was decided against. The deletion dialog's group is `AutofillContextAction.cancel`, so nothing is offered for saving. iOS has no Associated Domain (the EKP domain is not ours), so it has no strong-password suggestion; logins are filled from the passwords key.
- **Orientation:** portrait only, on tablets too: `SystemChrome.setPreferredOrientations` in `main()`, `screenOrientation="portrait"` on `MainActivity` and `UISupportedInterfaceOrientations` plus `UIRequiresFullScreen` in `Info.plist` (an iPad app that supports multitasking would have to rotate). Android 16 ignores the lock on large screens.
- **Registration of minors:** as in the official client, someone under 16 (`isUnder16`, from the PESEL or the picked date) is never sent to `auth/register`: `websiteRegistrationUri()` opens the website's form (`customerPageUrl` + `auth/register?…`) with what was typed.
- **User data:** `userDataProvider` is keyed on `AuthStatus`: cached copy served immediately and revalidated in the background, cache cleared on sign-out. Without a cached copy the load is the first one, and its failure ends the session. An answer is stored only for the session that asked for it (`_stillFor()`): the `ref` is taken before the request, because in a notifier `ref.mounted` after an `await` looks at the latest build's ref and does not notice a sign-out.
- **Dictionaries:** the `dictionary/*` lists that give type codes their names (`ticketKindsProvider`, `ticketLineScopesProvider`, `ticketPeriodsProvider`, `cityCardTypesProvider` in `core/providers/dictionary_providers.dart`) are kept as one JSON file each by `FileDictionaryCache` (`core/dictionaries/`). The server marks them `no-cache` and sends no `ETag` or `Last-Modified`, so the age rule is the app's own (`DictionaryController.maxAge`, 24 h): a stored copy is used as it is until then, an older one is returned at once and replaced in the background, and only a missing one makes the caller wait or can fail. The providers are lazy (nothing is requested until a screen watches one), ask the server only while signed in and after start-up, and their files stay across sign-out (public reference data). `transport-line` is a search and is not stored. A new dictionary is one more `Dictionary` constant plus its provider.
- **Errors:** UI text for a failed call goes through `describeError()` (`core/api/error_messages.dart`). Server messages are shown verbatim — the API only returns Polish.
- **l10n:** `lib/l10n/app_en.arb` is the template, `app_pl.arb` the Polish translation; add strings to both. Getter is non-nullable (`AppLocalizations.of(context)`).

### App tests

Widget tests pump the real `MobileKkmApp` through `pumpApp()` in `test/support/harness.dart`: a real `EkpClient` on top of `FakeAdapter` (canned replies keyed by method + path suffix, unmatched requests return 404), an `InMemoryTokenStore`, and fakes for the platform providers. Pass `session: signedInSession` to start signed in. Tests assert on `adapter.requests` / `requestTo()` and on `app.router`. Use `tapVisible()` and `field(label)` from the harness for form interaction.

The harness owns the `ProviderContainer` (`UncontrolledProviderScope`) and gives each test an in-memory drift database: disposing providers together with the widget tree would cancel drift's stream queries, whose clean-up timer the test framework reports as pending. Pass `database:` to seed one or to keep it across two `pumpApp` calls, `settle: false` when the splash is meant to stay up, and `tall: true` when a test looks at a whole lazily built list (the test font is wide, so cards are tall). A request without a canned reply (404) counts as "online, no config" for start-up; `account/user-data` alone has a default reply (`FakeAdapter.fallback`, set by `pumpApp`: an account with a card), since a signed-in app without user data signs out, and a test about a failing one says so with `fail`, `hold` or `reply`. A test that rests on a first load (a held request) switches animations off (`FakeAccessibilityFeatures(disableAnimations: true)`), since the placeholders' pulse never settles; Home's own placeholder has a progress bar that never does, so such a test leaves Home with `pump`. `openTab()`, `pullToRefresh()` and `app.location` cover the shell; `photoPicker:` takes a `FakePhotoPicker` (the picture the camera or gallery hands over; `onePixelPng` is one); `app.screen` (`FakeScreenSecurity`) records the screenshot protection and plays a screen recording, `app.scanDisplay` (`FakeScanDisplay`) records the display being turned up and kept awake; `app.container` reads providers no screen shows, and `dictionaryCache:` seeds the dictionaries (`InMemoryDictionaryCache`); `app.relay` is a second `FakeAdapter` for the aztec key relay (pass `relay:` to give it replies before the app starts; its paths are relative, `aztec-key` without a leading slash; without a reply the bundled key stays in use) and `aztecKeyStore:` seeds the stored key (`InMemoryAztecKeyStore`); `test/support/sample_data.dart` has synthetic tickets (also `ticketDetailJson()` for their details) and user data (`userDataJson(card: false)` or `detached: true` for an account behind the card set-up; user data without `mkkmData` always lands there). The ticket control test reads `ekp_api`'s synthetic contract fixture straight from `packages/ekp_api/test/fixtures/`.

`ekp_api` has its own, separate `MockAdapter` (`packages/ekp_api/test/mock_adapter.dart`): routes match by method + path *fragment* and serve replies as a FIFO queue, and an unregistered route throws.

## Design

`AppTheme` (`lib/core/theme/app_theme.dart`) is the design's token set: Material's fidelity scheme of `#303F9F` with the named roles pinned, `primaryContainer` the brand colour in both themes, the `AppColors` extension for success, the splash colours (each theme's surface, also in `pubspec.yaml` and `tool/render_branding.sh`), the type scale (Montserrat for display / headline / title, Inter for body / label) and the component themes (56 dp pill buttons, 64 dp app bar, radius-16 outlined fields, radius-28 cards, dialogs and sheets). Screens take their looks from there and from the shared widgets rather than styling locally:

- `RowGroup` / `GroupRow` with an `IconTile`: every list of rows (Account, the sheets, a ticket's "Manage", the purchase history).
- `MessageBanner` (error / success / info, optional action): server messages go here verbatim, at the top of a form. `AppStatusBanner` is the compact inverse strip for offline / unavailable; `offlineDetail` replaces its "Showing saved data." on a screen that shows what was typed.
- `FormCard` only for a form with several sections; a single group of fields sits straight on the surface. `LeadHeader` (tile, headline, one line of help) opens the lead screens, `AuthPage` frames them with an optional pinned bottom button.
- `CheckRow` for a checkbox with its label: level with the fields around it, the whole row toggles. Not Material's `Checkbox` / `CheckboxListTile`, whose padding sets the box in from the fields.
- `SystemBarScrim` around the body of a screen whose content scrolls under the system's navigation bar (ticket details): Android then draws its translucent scrim behind the three buttons. The app's bars are otherwise fully transparent, and such a screen is not put in a `SafeArea` for this. Not for screens that end in a bar or button of their own.
- `BulletCard` for a few points worth knowing before going on (the card set-up's welcome and photo rules). `Perforation` is the tear-off line of the ticket card and the mKKM card.
- `CodeScreen` for a screen that shows a code to someone else (see "Code screens" above); not a ring or a code panel of a screen's own.
- `EmptyStateCard` where a ticket or a list is missing or could not be loaded (`quiet` for a part of a screen, as under a ticket's details), `LoadProblem` for a failed load inside a sheet or a form, `SkeletonBox` shapes inside a `SkeletonPulse` while a first load is on its way (no centred spinner on a screen), `StatusChip` for a state (always icon and word, never colour alone).
- `showAppSnackBar()` for every snackbar: plain, `success` (check icon) or `error` (error icon, stays 6 s, can be closed). A spinner in a busy button is 18 dp with a 2 dp stroke in the button's foreground, and the button says what it is doing (`SubmitButton`, which takes a `style` for a smaller one).
- On the brand surface use the fixed roles (`primaryFixed`, `onPrimaryFixed`), never `primary`: in the light theme `primary` equals `primaryContainer`.
- A filled button inside a dialog takes `AppTheme.dialogAction` (40 dp); the global minimum is 56.

## Conventions

- Icons are Material Symbols Rounded: `Symbols.<name>_rounded` from `package:material_symbols_icons/symbols.dart`, not `Icons.*`. They are outlined by default (`iconTheme` in `AppTheme`); pass `fill: 1` for a filled one, e.g. the selected navigation destination.
- `always_use_package_imports` is enforced in the app: import as `package:mobile_kkm/...`, never relatively. (The packages use relative imports inside `lib/src/`.)
- Code is `dart format`-clean and `dart analyze` reports no issues; keep both that way.
- Generated files (`*.g.dart`, `*.freezed.dart`, `lib/l10n/app_localizations*.dart`) are excluded from analysis but not from `dart format`.
- `riverpod_lint` runs as an analyzer plugin (`plugins:` in the root `analysis_options.yaml`), for the app only.
- Lint rules shared by all members (correctness, performance, style) and the formatter width live in `analysis_options_shared.yaml`; each member's `analysis_options.yaml` includes it on top of `flutter_lints` (app) or `lints/recommended` (packages). Flutter-only rules and `always_use_package_imports` stay in the root file. Two rules shape everyday code: `always_put_control_body_on_new_line` — the formatter joins a brace-less `if (x) return;` back onto one line, so every control body needs braces — and `discarded_futures` — wrap intentional fire-and-forget calls in `unawaited(...)`.
- Commits follow Conventional Commits with a member scope: `feat(app): …`, `fix(ekp_api): …`, `chore: …`.
